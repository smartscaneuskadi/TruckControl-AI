# Refresco canónico de una suscripción

Candidata 0.5.25-rc.1; DDL71 aplicada una vez mediante Supabase oficial, SQL idéntico a la candidata CLI20261114080429. PostgreSQL aislado250/250 en Actions43576215731; frontend/backend ampliado todavía pendiente de promoción. No equivale a aceptación Stripe LIVE ni habilita cobros.

El botón «Actualizar suscripción» consulta ahora al proveedor **solo por acción del usuario** cuando el backend anuncia `refresh_available`. La carga de pantalla conserva el RPC de estado local: no inicia GET de Stripe ni consumo IA. Un backend anterior o sin la migración nueva mantiene `refresh_available=false` y la recarga local. La capacidad se consulta mediante un RPC exclusivo del servidor; no exige que el propietario introduzca otra clave ni un nuevo permiso. El interruptor opcional `TRUCKCONTROL_SUBSCRIPTION_REFRESH_SCHEMA_ACCEPTED=false` permite retirar únicamente este refresco.

El servidor autentica el JWT con Auth y `tc_verified_session`, deriva su usuario y SID verificados y selecciona la suscripción **propiedad de esa cuenta** según el mismo criterio del estado local: abierta primero, después la última terminal. No acepta empresa, precio, identificador de suscripción, rol ni estado enviados por el navegador. Esto permite conciliar una suscripción cancelada o caducada que conservaba `reconciliation_required=true` sin inventar un evento de Stripe ni esperar otra entrega.

Cada intento observa la revisión SQL antes del GET canónico de la suscripción. Comprueba ID, cliente, metadatos vinculados al usuario/solicitud nativos, una única línea mensual licenciada, cantidad, importe y moneda EUR. Verifica otra vez la misma sesión al regresar del proveedor. El commit SQL bloquea y comprueba los registros de Auth, el propietario, solicitud y suscripción; compara la revisión y guarda únicamente estado, fecha de periodo y cancelación. Una carrera obliga a **otra observación y otro GET**, hasta tres GET por petición. Las llamadas a Stripe comparten25segundos; las RPC nuevas tienen timeout individual5segundos, y la reautenticación conserva su transporte propio:25segundos no es un límite de toda la operación. Los errores upstream nunca se devuelven al navegador.

Antes de cada GET, SQL reserva un intento en la tabla privada e inmutable `tc_subscription_snapshot_refresh_attempts`. El bloqueo por cuenta impone como máximo tres observaciones en60segundos, incluidas respuestas fallidas y UUID distintos. Las siguientes reciben429 sin consultar al proveedor. La repetición de una operación ya completada no consume otro permiso. El registro no contiene claves, cabeceras, correos ni respuestas de Stripe.

La migración aditiva `20261114084109_subscription_explicit_snapshot_refresh.sql`, generada con CLI3.0.0, crea el recibo privado e inmutable `tc_subscription_snapshot_refreshes` y un RPC público invoker que delega en una función privada definer con `search_path=''`. Solo `service_role` tiene EXECUTE; anon/authenticated no acceden al recibo ni pueden fingir el resultado canónico. Un cierre de sesión o bloqueo ya confirmado impide el commit pendiente. El recibo conserva SID como evidencia UUID sin FK a `auth.sessions`, de modo que el cierre/purgado de sesiones continúa disponible.

No se escribe `event_created`, no se fabrica ID `evt_`, no se crea recibo de pago, mensualidad, factura fiscal ni aviso, y no se modifica la licencia o `paid_until`. El UUID de operación del navegador se conserva tras una respuesta incierta. Repetir un commit completado no actualiza de nuevo la revisión ni elimina una marca de conciliación posterior. La interfaz vuelve a consultar SQL y mantiene el error si no pudo confirmar el proveedor; no interpreta una recarga local como conciliación.
